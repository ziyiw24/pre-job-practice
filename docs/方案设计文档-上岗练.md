# 《上岗练》方案设计文档

> 文档版本：V1.0
> 编制日期：2026-09-14
> 对应需求文档：《需求分析文档-上岗练》V1.0
> 当前阶段：M0 核心业务闭环
> 工作名称：上岗练（非最终注册名称）

## 1. 文档目标

本文档用于指导上岗练从现有代码原型演进为可验证 MVP，重点解决以下问题：

1. 对比当前主流微信小程序开发技术并作出明确选型。
2. 设计最小核心流程：用户输入培训内容 → AI 生成题目 → 用户答题 → AI 生成分析报告。
3. 说明如何复用现有 Taro + FastAPI 项目，而不是重新开发。
4. 给出分阶段开发流程、模块边界、接口契约、AI 约束、测试与上线方案。
5. 明确当前阶段不引入登录、注册、MySQL、门店组织和员工管理等非必要依赖。

## 2. 已确认的范围与设计假设

### 2.1 业务边界

- 服务对象：中国大陆奶茶、咖啡、果饮等现制饮品门店。
- 长期形态：店长上传自有培训手册，审核并发布培训，员工完成学习与考核。
- 当前里程碑：先验证 AI 是否能将一段真实门店培训内容稳定转成可用题目和报告。
- 当前输入：优先支持直接粘贴文本；PDF/DOCX 上传放在核心闭环稳定后的下一阶段。
- 当前身份：只有匿名体验用户，不区分店长与员工。
- 当前数据：只做短期会话数据，不建设业务数据库。

### 2.2 M0 成功标准

用户可以在本地或体验环境完成以下流程，且不需要微信登录、MySQL、Redis、对象存储或向量数据库：

```text
粘贴一段培训内容
        ↓
后端校验并创建 AI 生成任务
        ↓
生成 3～5 道有原文依据的题目
        ↓
用户逐题作答并查看解析
        ↓
后端确定性计分
        ↓
AI 基于错题生成学习分析报告
```

验收指标：

- 一段 500～8000 字中文内容可以提交。
- 题目只考输入内容，不引用互联网常识补全门店规则。
- 每道题包含答案、解析、知识点和原文依据。
- 题目生成失败时页面可重试，不丢失用户输入。
- 报告得分由程序计算，AI 只负责解释和复习建议。
- 从输入到报告完整流程在真机微信小程序可运行。
- 没有模型密钥时，可使用演示模式跑通界面和状态流转。

## 3. 当前代码基线评估

### 3.1 已有技术栈

前端：

- Taro 4.1.11。
- React 18。
- TypeScript 5.1+。
- Sass。
- 微信小程序与 H5 构建目标。

后端：

- Python + FastAPI。
- Pydantic v2。
- LangChain OpenAI-compatible 模型接入。
- 异步出题任务与轮询接口。
- 现有 MySQL、Chroma、DashScope Embedding、微信登录和 COS 代码。
- Pytest 测试体系。

### 3.2 可直接复用

- `frontend/src/pages/quiz`：答题交互骨架。
- `frontend/src/pages/report`：报告展示骨架。
- `frontend/src/services/api.ts`：请求封装、异步任务轮询。
- `backend/app/models/quiz.py`：题目结构化模型。
- `backend/app/services/quiz_service.py`：出题编排。
- `backend/app/services/report_service.py`：评分与报告编排。
- `backend/app/repositories/task_repository.py`：无数据库时的内存任务模式。
- FastAPI 异常处理、配置、结构化日志和测试基础。

### 3.3 必须重构

- 首页从健康专题首页改成培训内容输入页。
- 删除 M0 核心路径对微信登录和用户知识库的依赖。
- 将健康领域字段和提示改成通用门店培训语义。
- Prompt 从健康知识问答改成门店 SOP 情景考核。
- 报告从健康掌握度改成培训通过情况、薄弱规则和复训建议。
- 页面之间不再通过 URL 携带完整题库 JSON；当前超长 URL 既不可靠，也会泄露答案。
- AI 模型、题目校验和降级策略需要成为独立模块。

### 3.4 暂时旁路而非删除

以下代码保留在仓库，但不进入 M0 请求链路：

- 微信登录与 JWT。
- MySQL 用户、历史和知识库表。
- PDF/DOCX 解析。
- Chroma 向量检索与 DashScope Embedding。
- 腾讯云 COS 和题目配图。
- 健康专题配置及相关接口。

待核心体验验证后再决定迁移、改写或删除，避免在产品方向仍可能变化时进行大规模不可逆清理。

## 4. 微信小程序技术选型对比

### 4.1 候选方案

本项目只比较三个现实候选：微信原生、Taro 4、uni-app。Flutter、React Native WebView 和自建跨端运行时不适合当前微信小程序单端验证阶段，不进入评分。

微信原生使用 WXML、WXSS 和 JavaScript/TypeScript，能最快获得微信最新 API 和渲染能力；官方框架包含视图层、逻辑层、基础组件、路由和微信 API。[微信小程序框架说明](https://developers.weixin.qq.com/miniprogram/dev/framework/MINA.html)

Taro 4 是跨端跨框架方案，可使用 React/Vue 等框架生成微信、支付宝、抖音等小程序及 H5；其 API 主要按微信小程序规范进行统一封装。[Taro 4 官方介绍](https://docs.taro.zone/docs/) [Taro API 说明](https://docs.taro.zone/docs/apis/about/desc/)

uni-app 以 Vue 单文件组件为主要开发范式，可编译到 H5、App 和微信小程序，但小程序端仍受平台语法及能力差异约束。[uni-app Vue 3 差异说明](https://uniapp.dcloud.net.cn/tutorial/vue3-basics.html)

### 4.2 选型评分

评分 1～5，5 为最优。权重针对当前项目，而不是通用结论。

| 维度 | 权重 | 微信原生 | Taro 4 + React | uni-app + Vue |
|---|---:|---:|---:|---:|
| 现有代码复用 | 30% | 1 | 5 | 1 |
| 最新微信能力跟进 | 20% | 5 | 4 | 3 |
| 独立开发效率 | 20% | 3 | 5 | 4 |
| 微信端兼容与调试 | 15% | 5 | 4 | 4 |
| H5/其他端复用 | 10% | 1 | 5 | 5 |
| 迁移及维护风险 | 5% | 2 | 5 | 2 |
| 加权结果 | 100% | 3.10 | **4.65** | 2.80 |

### 4.3 最终选择

**继续使用 Taro 4.1.11 + React 18 + TypeScript，不迁移框架。**

原因：

1. 当前代码已使用 Taro 4.1.11，迁移不会为核心业务验证增加用户价值。
2. 输入、加载、答题和报告属于普通表单与卡片交互，不是原生动画或复杂长列表性能场景。
3. H5 可以作为快速视觉预览，微信小程序作为最终验收端。
4. React 组件、类型和服务层未来可复用到店长 Web 管理端。
5. Taro 官方 4.x 文档仍持续维护，并提供多小程序和 H5 目标。

### 4.4 应对小程序快速迭代

跨端框架可能晚于微信更新。Taro 官方也说明，平台特有 API 可能尚未完成统一适配，此时可以使用对应平台命名空间。[Taro API 说明](https://docs.taro.zone/docs/apis/about/desc/)

项目采用以下策略：

- 锁定所有 `@tarojs/*` 包为同一精确版本，禁止混用不同小版本。
- 每月设置一次依赖升级窗口，不在功能开发中途追新。
- 微信独有能力封装在 `src/adapters/wechat.ts`，业务组件不直接散落 `wx.*` 调用。
- 使用 `Taro.canIUse` 做能力检测并提供降级提示。
- H5 只承担开发预览；文件选择、分享、隐私授权和真机样式必须在微信开发者工具与真机验收。
- 每次升级执行生产构建、包体积检查和 3 台设备冒烟测试。
- 不在 M0 启用 Skyline。Skyline 用于替代 WebView 并改善复杂交互性能，但当前页面没有足以抵消兼容和调试成本的性能问题。[微信官方 Skyline 示例仓库](https://github.com/wechat-miniprogram/awesome-skyline)

### 4.5 何时考虑改用微信原生

只有出现以下情况之一才重新评估：

- 产品确认长期只做微信，且 Taro 阻塞关键微信能力超过两个发布周期。
- 大量使用 Skyline/Worklet、自定义路由或复杂手势动画。
- 真机出现无法通过组件级优化解决的渲染性能问题。
- 小程序审核问题被确认来自跨端框架产物。

uni-app 不建议作为本项目的迁移目标，因为它会引入 React → Vue 的整体重写，但不会消除小程序平台本身的限制。

## 5. 总体技术架构

### 5.1 M0 架构

```text
┌───────────────────────────────┐
│ 微信小程序 / H5               │
│ Taro + React + TypeScript     │
│                               │
│ 输入页 → 等待页 → 答题 → 报告 │
│ 会话状态：Taro Storage        │
└──────────────┬────────────────┘
               │ HTTPS JSON
┌──────────────▼────────────────┐
│ FastAPI                       │
│ 输入校验 / 任务编排 / 计分    │
│ Pydantic Schema / 错误处理     │
└─────────┬──────────┬──────────┘
          │          │
┌─────────▼────┐ ┌───▼──────────┐
│ TaskStore    │ │ ModelGateway  │
│ 内存 + TTL   │ │ OpenAI 兼容层 │
└──────────────┘ └───┬──────────┘
                     │
             ┌───────▼──────────┐
             │ 国内大模型 API   │
             └──────────────────┘
```

M0 不使用数据库。任务存在单进程内存中并设置 30 分钟 TTL；小程序用本地存储保存当前输入、题库、答题记录和报告缓存。

此模式只适用于本地开发和单实例体验环境。腾讯云文档明确说明云托管实例可能被销毁、重建或横向扩容，无状态容器不应依赖本地内存或文件持久化。[CloudBase Run 无状态要求](https://cloud.tencent.com/document/product/1243/49230)

### 5.2 M1 架构演进

核心闭环验证后再引入：

- 对象存储：保存店长上传的 PDF/DOCX。
- 文档解析：提取页码、段落和表格文本。
- Redis：保存异步任务、幂等键、限流和短期会话。
- MySQL：保存门店、成员、课程、题目、发布任务和答题记录。
- 向量检索：只在长文档超过模型上下文或需要跨文档检索时使用。

不要为了 10 页左右的手册在 M0 预先引入向量数据库。短文本直接送入模型可以减少检索遗漏、Embedding 成本和部署依赖。

### 5.3 部署选择

| 方案 | M0 | 正式 MVP | 判断 |
|---|---|---|---|
| 本地 FastAPI | 推荐 | 不适用 | 开发最快 |
| 微信云托管 / CloudBase Run | 可选 | 推荐 | 可直接部署现有 Docker/FastAPI，贴近微信生态 |
| 云函数 | 不推荐 | 可用于轻接口 | AI 长请求、文档解析和 Python 依赖管理更受限 |
| 自购云服务器 | 可选 | 可选 | 自由度高，但增加安全、证书和运维负担 |

腾讯云建议微信小程序后端优先考虑微信云托管；云托管支持基于 Dockerfile 的任意语言服务。FastAPI 可直接作为 Python 容器运行。[微信云托管建议](https://cloud.tencent.com/document/product/1243/59521) [CloudBase FastAPI 容器示例](https://cloudbase.cloud.tencent.com/products/cloudrun)

M0 若部署云托管，应固定单实例且明确允许任务在实例重启时丢失；M1 引入 Redis 后再开放弹性伸缩。

## 6. 前端方案设计

### 6.1 页面结构

M0 只保留四个核心页面：

```text
pages/input/index     输入培训内容
pages/generating/index 生成进度与失败重试
pages/quiz/index      答题与逐题解析
pages/report/index    培训分析报告
```

首页、健康专题、知识库和个人中心不进入 M0 主导航。为避免立即删除旧代码，可通过构建配置或 feature flag 暂时隐藏。

### 6.2 输入页

字段：

- 培训标题：可选，最多 60 字。
- 培训内容：必填，500～8000 个中文字符。
- 题目数量：默认 5，支持 3 或 5。
- 难度：默认混合，不在首屏暴露复杂设置。

交互：

- 提供“粘贴示例”按钮，使用脱敏后的奶茶店手册片段。
- 实时显示字数和预计题量。
- 内容保存在本地草稿，生成失败后可返回继续编辑。
- 明确提示“AI 生成内容需人工确认，不替代门店正式制度”。
- 禁止输入为空、纯重复字符或明显超长内容。

### 6.3 生成页

- 前端创建任务后跳转到独立生成页。
- 每 1.2 秒轮询一次，采用最大时长 120 秒。
- 页面进入后台后降低轮询频率，回到前台立即查询一次。
- 状态文案分为：正在读取 → 正在整理考点 → 正在生成题目 → 正在校验。
- 超时不等于任务失败，允许用户重新查询。
- 使用 `client_request_id` 避免用户重复点击创建多个任务。

### 6.4 答题页

- 一屏一道题，显示当前进度。
- 首版支持单选与判断题；情景单选仍使用单选数据结构。
- 选择答案后先本地记录，点击确认才展示答案与解析。
- 解析展示：正确答案、原因、知识点、原文依据。
- 不允许在未答题时直接显示答案。
- 切后台或异常退出后，可从本地恢复当前题号和答案。

### 6.5 报告页

由后端返回：

- 得分和正确率。
- 掌握较好的知识点。
- 需要复习的规则。
- 逐项错误原因。
- 3 条具体复习建议。
- 风险提示：线上结果不等同于实操上岗认证。

不显示虚假经验值、排行榜、营销海报或与学习结果无关的装饰指标。

### 6.6 页面间状态传递

禁止继续使用：

```text
/pages/quiz/index?quizData=<完整 JSON>
```

目标方式：

```text
Taro.setStorageSync('active_quiz:<task_id>', quizData)
Taro.navigateTo({ url: `/pages/quiz/index?taskId=${taskId}` })
```

路由只传 `taskId`/`quizId`。页面先读本地缓存，缺失时再调用后端查询。正式员工考核阶段，正确答案不能提前返回客户端，应改成服务端判分。

### 6.7 前端目录建议

```text
frontend/src/
├── adapters/
│   ├── storage.ts
│   └── wechat.ts
├── components/
│   ├── SourceEvidence.tsx
│   ├── QuestionCard.tsx
│   └── ErrorState.tsx
├── features/training/
│   ├── models.ts
│   ├── training.api.ts
│   ├── training.store.ts
│   └── training.validators.ts
├── pages/
│   ├── input/
│   ├── generating/
│   ├── quiz/
│   └── report/
└── app.config.ts
```

M0 不引入 Redux。当前状态规模可用页面状态 + 独立 service + Taro Storage 管理；当门店、员工、课程出现跨页面复杂状态后再评估 Zustand 或 Redux Toolkit。

## 7. 后端方案设计

### 7.1 分层结构

```text
HTTP Route
   ↓
Request Validation
   ↓
Training Use Case
   ├── InputGuard
   ├── PromptBuilder
   ├── ModelGateway
   ├── OutputValidator
   └── TaskStore
   ↓
Response Schema
```

路由不直接调用模型，Prompt 不读取 HTTP 对象，模型供应商代码不进入业务 service。

### 7.2 模型接入选择

采用 OpenAI-compatible Provider Adapter，而不是绑定具体厂商：

```python
class ModelGateway(Protocol):
    async def generate_quiz(self, request: QuizDraftRequest) -> QuizDraft: ...
    async def generate_report(self, request: ReportRequest) -> TrainingReport: ...
```

生产首选国内可合规采购的模型平台，具体模型通过环境变量设置。腾讯 TokenHub、腾讯混元和阿里云百炼均提供 OpenAI 兼容接口，可在较少代码改动下切换供应商。[腾讯 TokenHub](https://cloud.tencent.com/document/product/1823/130079) [阿里云百炼](https://help.aliyun.com/zh/model-studio/what-is-model-studio/)

当前仓库可以继续使用 DeepSeek 配置完成开发，但需完成同一测试集上的质量、成本、延迟和数据条款评估后才能确定生产模型。不要把厂商名写进业务字段或数据库结构。

### 7.3 是否使用 LangChain

M0 建议：

- 保留现有 `langchain-openai` 以减少改造量。
- 只使用模型调用和结构化输出能力。
- 核心流程不使用 Agent、LangGraph、Tavily、Chroma 和工具调用。
- 将 LangChain 限制在 `infrastructure/llm` 目录，业务层只依赖 `ModelGateway`。

如果结构化输出在不同模型间兼容性不稳定，后续改成官方 OpenAI-compatible SDK + JSON Schema + Pydantic 二次校验，不影响上层业务。

### 7.4 任务模型

```python
class GenerationTask:
    task_id: str
    client_request_id: str
    status: Literal['pending', 'running', 'completed', 'failed']
    progress_stage: Literal['reading', 'extracting', 'generating', 'validating']
    result: QuizDraft | None
    error_code: str | None
    created_at: datetime
    expires_at: datetime
```

TaskStore M0 实现：线程安全内存字典 + TTL 清理；测试中可注入 fake clock。M1 实现 Redis，业务接口保持不变。

### 7.5 确定性评分

AI 不能负责计算分数。服务端逻辑：

```text
逐题标准化 selected_answers
        ↓
与标准答案进行集合比较
        ↓
统计正确数、总数、正确率
        ↓
提取错题知识点与来源
        ↓
把确定性结果交给 AI 生成解释
```

即使报告模型调用失败，也必须返回基础报告：得分、错题、正确答案和原文依据。

### 7.6 错误代码

| code | 场景 | 用户提示 |
|---|---|---|
| `CONTENT_TOO_SHORT` | 内容不足 500 字 | 请粘贴更完整的培训内容 |
| `CONTENT_TOO_LONG` | 超过输入限制 | 请分章节生成 |
| `CONTENT_UNUSABLE` | 无有效规则或大量乱码 | 暂未识别到可考核内容 |
| `MODEL_BUSY` | 模型限流/拥塞 | 服务繁忙，请稍后重试 |
| `MODEL_TIMEOUT` | 模型超时 | 生成时间较长，可重新查询 |
| `OUTPUT_INVALID` | 输出不满足 Schema | 题目校验失败，请重试 |
| `INSUFFICIENT_EVIDENCE` | 无法找到原文依据 | 资料依据不足，未生成题目 |
| `TASK_EXPIRED` | 内存任务已过期 | 本次生成已过期，请重新生成 |

对用户隐藏供应商错误栈和密钥信息；日志只记录 request ID、模型、耗时、token 数和错误类别，不记录完整手册内容。

## 8. API 设计

统一前缀：`/api/v1/training`。旧 `/quiz` 接口在迁移期保留兼容适配，前端新代码不再新增依赖。

### 8.1 创建题目生成任务

`POST /api/v1/training/generate/async`

请求：

```json
{
  "client_request_id": "01J...",
  "title": "原料时效培训",
  "content": "所有开封食材必须标注……",
  "question_count": 5,
  "difficulty": "mixed"
}
```

响应：

```json
{
  "task_id": "task_xxx",
  "status": "pending"
}
```

规则：同一 `client_request_id` 在 TTL 内返回同一个任务，避免重复扣费。

### 8.2 查询生成任务

`GET /api/v1/training/tasks/{task_id}`

完成响应：

```json
{
  "task_id": "task_xxx",
  "status": "completed",
  "progress_stage": "validating",
  "result": {
    "quiz_id": "quiz_xxx",
    "title": "原料时效培训",
    "summary": "重点考核标签、保存时间和异常处理",
    "ai_generated": true,
    "questions": []
  }
}
```

### 8.3 生成报告

`POST /api/v1/training/reports`

请求：

```json
{
  "quiz_id": "quiz_xxx",
  "questions": [],
  "answer_records": [
    {
      "question_id": "q1",
      "selected_answers": ["B"],
      "duration_ms": 8200
    }
  ]
}
```

响应：

```json
{
  "score": 80,
  "correct_count": 4,
  "total_count": 5,
  "result": "needs_review",
  "mastered_points": ["开封标签"],
  "weak_points": ["超时物料处理"],
  "review_actions": ["重新阅读超时物料处理规则"],
  "ai_summary": "你已经掌握标签要求……",
  "ai_generated": true
}
```

M0 为了匿名体验允许客户端携带题目；M1 发布培训后，报告接口只接收 `quiz_id + answers`，标准答案必须从服务端读取。

### 8.4 演示能力

`GET /api/v1/training/demo`

返回一段脱敏示例内容，用于无模型密钥或首次体验。不要把用户提供的完整手册作为公开默认内容。

## 9. 数据结构设计

### 9.1 题目模型

```python
class Evidence(BaseModel):
    quote: str
    start_offset: int | None = None
    end_offset: int | None = None
    page_number: int | None = None

class TrainingQuestion(BaseModel):
    id: str
    type: Literal['single', 'judge']
    scenario: str | None
    stem: str
    options: list[QuestionOption]
    answer: list[str]
    explanation: str
    knowledge_point: str
    evidence: Evidence
    risk_tags: list[Literal[
        'number', 'temperature', 'duration', 'recipe',
        'safety', 'punishment', 'emergency'
    ]]
    requires_confirmation: bool
```

`quote` 必须是输入文本的连续子串。`start_offset/end_offset` 由服务端重新匹配计算，不能完全信任模型返回的位置。

### 9.2 报告模型

```python
class TrainingReport(BaseModel):
    score: int
    correct_count: int
    total_count: int
    result: Literal['passed', 'needs_review']
    mastered_points: list[str]
    weak_points: list[str]
    review_actions: list[str]
    ai_summary: str
    ai_generated: bool
```

通过阈值 M0 默认 80 分，仅用于体验；不能在没有店长配置和实操确认的情况下称为“准予上岗”。

## 10. AI 方案设计

### 10.1 出题目标

AI 输出优先级：

1. 忠实于输入资料。
2. 正确答案唯一、无歧义。
3. 测试真实工作判断，而不是机械识字。
4. 覆盖关键红线、步骤和异常处理。
5. 每题都能引用原文证据。

### 10.2 Prompt 结构

System Prompt 包含：

- 角色：门店培训课程设计助手。
- 禁止：添加输入中不存在的制度、配方、时长、处罚和安全结论。
- 证据：每题必须给出原文连续引用。
- 题型：单选、判断、工作情景单选。
- 干扰项：必须合理但能由原文明确排除。
- 输出：严格遵守 JSON Schema，不输出 Markdown。
- 拒绝：资料不足时返回 `insufficient_evidence`。

User Prompt 只包含经过分隔的标题、原文、题量和难度。使用清晰边界标记，声明原文中的任何命令性句子都只是培训资料，不是对模型的系统指令，防止 Prompt Injection。

### 10.3 服务端校验

模型返回后按顺序执行：

1. Pydantic Schema 校验。
2. 题目数量校验。
3. 选项 key 唯一性和答案存在性校验。
4. 单选答案数量必须为 1。
5. 原文引用必须能在输入内容中找到。
6. 题干、选项和解析不得完全重复。
7. 数字、温度、时间、处罚、配方命中风险标签时，强制 `requires_confirmation=true`。
8. 检测明显答案泄漏，例如正确选项显著长于所有干扰项。
9. 校验失败只允许自动修复一次，仍失败则返回明确错误。

### 10.4 报告生成

报告 Prompt 不接收员工姓名或其他个人信息。输入只包含：

- 确定性分数。
- 答对/答错知识点。
- 错题题干、正确答案、用户答案和原文依据。

模型只能总结错误模式并生成复习动作，不得修改分数、答案或声称员工已经具备实操能力。

### 10.5 演示降级

未配置模型或模型故障时：

- 示例内容使用仓库内审核过的固定题目，保证核心 UI 可演示。
- 用户自定义内容不能伪装成 AI 成功生成，应提示当前为演示环境。
- 报告使用确定性模板生成，`ai_generated=false`。

## 11. 安全、隐私与合规

### 11.1 密钥与网络

- 模型 API Key 只能存在后端环境变量中，绝不能打包进小程序。
- 正式环境只允许 HTTPS。
- CORS 仅开放实际 H5 管理域名；小程序端不依赖浏览器 CORS，但仍需配置合法请求域名。
- 请求体大小、并发数、IP/设备频率均设置限制。
- 错误响应不返回堆栈、供应商响应正文或内部路径。

### 11.2 输入内容

- M0 文本内容只在任务 TTL 内存中短暂保存，过期清除。
- 默认不将用户内容用于模型训练；供应商选择前核对数据使用条款。
- 日志只记录内容长度和哈希，不记录完整手册。
- 对输入进行 Prompt Injection 隔离、控制字符清理和最大长度限制。

### 11.3 AI 标识

所有 AI 生成题目、解析和报告显示“AI 生成草稿”标识。《人工智能生成合成内容标识办法》自 2025 年 9 月 1 日起施行，并要求适用主体按规则提供显式或隐式标识；正式上线前需结合产品开放范围评估适用义务。[国家网信办](https://www.cac.gov.cn/2025-03/14/c_1743654685899683.htm)

### 11.4 小程序隐私

M0 不申请头像、昵称、手机号、定位和通讯录权限。M1 增加聊天文件选择和微信登录时，再配置对应隐私保护指引及授权流程。微信规则要求涉及个人信息的小程序先声明相应用途并完成用户同意后调用相关隐私接口。[腾讯云对微信隐私规则的说明](https://cloud.tencent.cn/document/product/1301/97930)

## 12. 性能与成本设计

### 12.1 性能目标

| 指标 | M0 目标 |
|---|---:|
| 首页可交互 | 真机冷启动后 2 秒内 |
| 创建任务接口 | 500ms 内返回 task ID |
| 5 题生成 P50 | 30 秒内 |
| 5 题生成 P95 | 90 秒内 |
| 任务状态查询 | P95 300ms 内 |
| 本地切题响应 | 100ms 内 |
| 基础报告生成 | 1 秒内 |
| AI 报告 P95 | 30 秒内 |

### 12.2 模型成本控制

- M0 限制输入 8000 字、题量最多 5。
- 不调用联网搜索、图片生成或 Embedding。
- 题目生成和报告各调用一次模型；结构修复最多额外一次。
- 通过输入哈希在短 TTL 内复用相同结果。
- 记录输入/输出 token、耗时、供应商和模型，建立每次完整流程成本。
- 设置每日总预算和单 IP/设备生成次数限制。

## 13. 测试方案

### 13.1 后端单元测试

- 输入长度、空白、乱码和重复字符校验。
- 题目 Schema、选项和答案校验。
- 证据引用必须存在于原文。
- 风险标签识别。
- 确定性计分。
- TaskStore TTL、幂等和状态迁移。
- 模型超时、限流、非法 JSON 和证据不足降级。

### 13.2 Prompt 契约与评测集

建立 `backend/tests/fixtures/training_cases/`，至少包括：

- 奶茶店上岗纪律。
- 食材标签和保存时效。
- 点单复核和错单处理。
- 设备停机和火情应急。
- 含相互矛盾数字的资料。
- 很短、无规则、广告化或包含 Prompt Injection 的资料。

每次修改 Prompt 或模型时执行：

- 证据命中率必须 100%。
- 答案可由原文唯一推出的比例 ≥ 95%。
- 关键红线覆盖率 ≥ 80%。
- 人工抽检无新增门店规则。
- 相同测试集记录模型成本和 P95 延迟。

### 13.3 前端测试

- 输入草稿恢复。
- 防重复提交。
- 轮询状态和超时恢复。
- 答题进度、解析和重进恢复。
- 报告正确率与后端一致。
- 无超长 URL、无答案出现在日志或路由中。

### 13.4 真机测试

至少覆盖：

- iPhone 近两代系统。
- 一台中低端 Android。
- 一台较新 Android。
- Wi-Fi、4G/5G、弱网和切后台恢复。
- 微信开发者工具生产构建与体验版扫码。

## 14. 开发流程与分步实施

### 阶段 0：冻结基线（0.5 天）

目标：保证改造过程可回归。

- 记录当前本地启动方式和环境变量。
- 执行后端测试、H5 构建、微信生产构建。
- 保存核心页面截图。
- 把旧健康功能放到 feature flag 后，不立即删除。

完成标准：现有测试全部通过，改造前行为可复现。

### 阶段 1：匿名文本出题 API（1～2 天）

目标：不依赖登录和数据库生成可追溯题目。

- 新建 training request/response models。
- 新建匿名生成路由。
- 抽象 `ModelGateway`。
- 改写门店培训出题 Prompt。
- 加入引用、风险标签和输出校验。
- 使用内存 TaskStore + TTL + 幂等 ID。
- 保留无模型密钥演示降级。

完成标准：用奶茶手册文本片段调用 API，返回 5 道通过契约校验的题目。

### 阶段 2：输入和生成页面（1～2 天）

目标：从小程序完成内容提交并看到题目。

- 首页改为内容输入页。
- 增加字数、草稿和示例。
- 增加生成状态页及重试。
- 路由只传 task ID，题目放本地缓存。
- 移除核心路径登录等待。

完成标准：无微信登录、无 MySQL 时可从首页进入答题页。

### 阶段 3：答题与确定性报告（1 天）

目标：完成稳定的答题和报告闭环。

- 改造题目模型和原文依据展示。
- 本地保存答题进度。
- 后端确定性计分。
- AI 报告失败时返回模板报告。
- 报告页面改为门店培训语义。

完成标准：刷新或切后台后仍能继续，报告分数完全正确。

### 阶段 4：AI 质量与安全（1～2 天）

目标：让题目可以用于真实用户测试，而非只完成演示。

- 建立至少 20 段真实/脱敏训练材料评测集。
- 增加 Prompt Injection、数字冲突、证据不足用例。
- 人工审查 100 道生成题。
- 确定首个生产候选模型并记录质量、延迟和成本。

完成标准：达到第 13.2 节的评测阈值。

### 阶段 5：体验版验证（1 天）

- Docker 化部署 FastAPI。
- 配置测试域名、HTTPS 和小程序合法请求域名。
- 配置 API Key、限流、预算告警和脱敏日志。
- 微信开发者工具上传体验版。
- 邀请 3 位店长完成同一测试任务。

完成标准：真机核心流程成功率 ≥ 95%，无阻断错误。

### 阶段 6：PDF 上传（核心闭环通过后）

- 接入 `chooseMessageFile` 和上传进度。
- 文件暂存对象存储，不保存在容器本地磁盘。
- PDF/DOCX 解析保留页码。
- 10 页左右文档优先整文生成；超长内容再分章节或检索。
- 增加店长审核页。

微信聊天文件选择本身属于隐私相关能力，上线时必须同步完善隐私声明。M0 先做粘贴文本可以减少首次审核和联调变量。

### 阶段 7：账号、门店和员工（PDF 流程验证后）

此时才引入：

- 微信登录和 JWT。
- MySQL 数据库。
- 门店、成员和角色。
- 培训发布、培训码和员工成绩。
- Redis 异步任务。

## 16. 发布与回滚

### 16.1 发布路径

```text
本地单元测试
 → H5 快速预览
 → 微信开发者工具
 → 开发版
 → 内部体验版
```

### 16.2 Feature Flags

- `ENABLE_TRAINING_CORE`：新培训流程。
- `ENABLE_LEGACY_HEALTH_TOPICS`：旧健康专题，默认关闭。
- `ENABLE_DOCUMENT_UPLOAD`：PDF/DOCX 上传。
- `ENABLE_AUTH`：登录与门店身份。
- `ENABLE_AI_REPORT`：AI 报告；关闭时使用确定性报告。

### 16.3 回滚

- 后端保留上一稳定镜像。
- Prompt 版本化，可单独回滚，不必回滚整个应用。
- 模型供应商配置可切换到备用 provider。
- 小程序体验版验证通过后才提交正式版；正式版故障时优先关闭 AI 报告和生成入口，保留错误说明。

## 17. 关键技术决策记录（ADR）

| 编号 | 决策 | 原因 | 复审条件 |
|---|---|---|---|
| ADR-001 | 保留 Taro 4 + React | 最大化现有代码复用 | Taro 阻塞关键微信能力 |
| ADR-002 | M0 不做登录和数据库 | 它们不影响核心价值验证 | 进入门店多人试用 |
| ADR-003 | M0 先粘贴文本，再上传文件 | 降低文件解析、存储和隐私变量 | 文本闭环质量达标 |
| ADR-004 | AI 不负责计分 | 避免不确定计算错误 | 永不复审 |
| ADR-005 | 题目必须有原文证据 | 产品可信度的基础 | 永不复审 |
| ADR-006 | 不使用联网搜索 | 门店规则只能来自店长资料 | 永不复审，除非独立行业知识模式 |
| ADR-007 | M0 不使用向量数据库 | 短文直接输入更简单可靠 | 文档超过上下文或跨文档检索 |
| ADR-008 | 路由只传 ID | 避免超长 URL、泄露和解析失败 | 永不复审 |

## 19. 最终实施建议

第一轮开发只实施阶段 0～3。最短路径是复用现有 quiz/report 页面和 FastAPI 服务，新增匿名文本输入协议、门店培训 Prompt、证据校验及报告语义，同时切断核心路径对登录、MySQL、知识库和健康专题的依赖。

当且仅当该流程能基于用户提供的奶茶店手册稳定生成高质量情景题，并在真机上完成答题和报告，才进入 PDF 上传；PDF 流程通过后再建设账号、门店、员工和数据库。这样每一步都验证一个新的产品风险，不会先把时间花在尚未被证明需要的基础设施上。
