## 2. 项目定位与不可破坏的原则

### 2.1 产品定位

上岗练是面向奶茶、咖啡、果饮等现制饮品门店的 AI 培训工具。店长提供自有培训手册，系统将纸面制度转换为可练习、可追溯、可复盘的岗位题目。

核心闭环：

```text
店长提供培训内容
        ↓
AI 提取规则并生成情景题
        ↓
程序与 Agent 完成证据校验和质量审查
        ↓
店长人工确认后发布
        ↓
员工答题
        ↓
服务端确定性判分 + AI 复训建议
```

### 2.2 五条强约束

1. 题目只能依据店长提供的资料，不使用联网常识补全门店制度。
2. 每道题必须附带可在原文中逐字找到的证据。
3. 数字、温度、时效、配方、处罚和安全规则必须标记人工复核。
4. 成绩由程序计算，AI 不得计算或修改得分。
5. 线上答题结果不等同于实操上岗认证。

## 6. 目标架构与演进原则

### 6.1 目标分层

```text
Taro 小程序 / 店长 Web 管理端
              ↓
FastAPI Route + Auth + Tenant Guard
              ↓
Application Use Cases
  ├─ Training Generation
  ├─ Review & Publish
  ├─ Employee Assignment
  └─ Answer & Report
              ↓
Domain Services
  ├─ Deterministic Validator
  ├─ Scoring Service
  ├─ Document Parser
  └─ Retrieval Service
              ↓
LangGraph Training Authoring Agent
  规则提取 → 题目规划 → 生成 → 评审 → 修订/人工确认
              ↓
Provider Adapters
  LLM / Redis / MySQL / COS / Chroma / WeChat
```

### 6.2 编码原则

- 路由只做请求解析和响应组装，不直接调用模型。
- 业务 Service 不依赖 DeepSeek、COS 或 Redis 具体 SDK，只依赖 Protocol/Interface。
- LLM 输出首先通过 Pydantic，再通过确定性验证器。
- Agent 只决定需要推理的路径；计分、权限、幂等、限流和证据子串匹配仍由程序处理。
- 每个 Prompt 都有版本号，每个 Agent 任务记录 graph/prompt/model 版本。
- 所有外部依赖都必须可被 fake 实现替换，测试不调用真实模型和云服务。

## 11. M1-3：LangGraph 质检修订 Agent

### 11.1 目标

把当前单次生成升级为可观测、可中断、可有限次修订的 Agent 工作流：

```text
extract_rules
      ↓
plan_quiz
      ↓
generate_quiz
      ↓
validate_deterministically
      ↓
review_quiz
      ↓
route_after_review
  ├─ 合格 → finalize
  ├─ 可修订且次数 < 2 → rewrite_quiz → validate/review
  └─ 高风险或超次数 → await_human_review
```

### 11.2 为什么这是 Agent

关键不是使用了 LangGraph，而是系统会基于运行状态动态选择：

- 直接完成。
- 只重写失败题目。
- 进入人工审核。
- 达到成本/迭代上限后停止。

### 11.3 Agent State

新建 `backend/app/agents/training/state.py`：

```python
from typing import Literal, TypedDict

class ReviewIssue(TypedDict):
    question_id: str
    code: Literal[
        "EVIDENCE_MISSING",
        "ANSWER_AMBIGUOUS",
        "NUMBER_CONFLICT",
        "OPTION_LEAKAGE",
        "RULE_NOT_COVERED",
        "UNSUPPORTED_CLAIM",
    ]
    detail: str
    severity: Literal["low", "medium", "high"]

class TrainingAgentState(TypedDict):
    task_id: str
    title: str
    content: str
    question_count: int
    difficulty: str
    extracted_rules: list[dict]
    quiz_plan: list[dict]
    questions: list[dict]
    deterministic_issues: list[ReviewIssue]
    critic_issues: list[ReviewIssue]
    revision_count: int
    max_revisions: int
    token_usage: int
    model_calls: int
    status: Literal["running", "awaiting_review", "completed", "failed"]
    prompt_version: str
    graph_version: str
```

State 中不存密钥，不存用户身份数据。日志中不输出完整 `content`。

### 11.4 节点设计

#### `extract_rules`

输出结构：

```python
class ExtractedRule(BaseModel):
    rule_id: str
    category: Literal["procedure", "prohibition", "exception", "safety", "service"]
    statement: str
    evidence: Evidence
    risk_tags: list[RiskTag]
    priority: Literal["must", "should", "optional"]
```

节点只提取，不出题。程序再次验证 `evidence.quote in content`。

#### `plan_quiz`

输出每题要覆盖的 `rule_id`、题型、场景和难度，不生成选项。规划器优先覆盖：

1. must + safety。
2. 禁止项和异常处理。
3. 普通步骤。
4. 不在同一组题重复考察同一规则。

#### `generate_quiz`

仅根据 `quiz_plan + extracted_rules` 出题，不再把无关原文全部交给模型。每题需指向 `rule_id`。

#### `validate_deterministically`

这是普通 Python 节点，不调用 LLM，检查：

- Pydantic Schema。
- 题量、题号和选项 key。
- 单选答案唯一。
- quote 及 offset。
- 题目中出现的数字是否可在对应规则中找到。
- 题干/解析是否直接泄露正确选项。
- `requires_confirmation` 是否按风险标记。

#### `review_quiz`

Critic 只做语义评审：正确答案是否唯一、干扰项是否合理、场景是否真实、是否存在原文不支持的结论。Critic 不得修改题目。

#### `rewrite_quiz`

只接收失败题、对应规则和 issue，不重写已通过题。每轮 `revision_count += 1`。

#### `await_human_review`

在 M1 先将状态返回前端，不必立即引入后台。M3 接入 LangGraph interrupt/checkpoint，等店长修改或确认后 resume。

### 11.5 条件路由

```python
def route_after_review(state: TrainingAgentState) -> str:
    issues = state["deterministic_issues"] + state["critic_issues"]
    if not issues:
        return "finalize"
    if any(issue["severity"] == "high" for issue in issues):
        return "await_human_review"
    if state["revision_count"] >= state["max_revisions"]:
        return "await_human_review"
    return "rewrite_quiz"
```

禁止无上限自动反思。M1 默认 `max_revisions=2`、`max_model_calls=6`，并设置整任务超时。

### 11.6 Graph 编排

新建 `backend/app/agents/training/graph.py`：

```python
builder = StateGraph(TrainingAgentState)
builder.add_node("extract_rules", extract_rules)
builder.add_node("plan_quiz", plan_quiz)
builder.add_node("generate_quiz", generate_quiz)
builder.add_node("validate", validate_deterministically)
builder.add_node("review", review_quiz)
builder.add_node("rewrite", rewrite_quiz)
builder.add_node("human_review", await_human_review)
builder.add_node("finalize", finalize)

builder.add_edge(START, "extract_rules")
builder.add_edge("extract_rules", "plan_quiz")
builder.add_edge("plan_quiz", "generate_quiz")
builder.add_edge("generate_quiz", "validate")
builder.add_edge("validate", "review")
builder.add_conditional_edges("review", route_after_review, {
    "rewrite_quiz": "rewrite",
    "await_human_review": "human_review",
    "finalize": "finalize",
})
builder.add_edge("rewrite", "validate")
builder.add_edge("human_review", END)
builder.add_edge("finalize", END)
training_graph = builder.compile()
```

M1 内存运行即可；M2/M3 再接 Redis checkpointer。

## 14. M3：PDF/DOCX 上传、解析与人工审核


### 14.2 使用技术

- Taro `chooseMessageFile`：从微信会话选择 PDF/DOCX。
- `Taro.uploadFile`：上传与进度。
- 腾讯云 COS：原始文件和解析产物。
- `pypdf` + `docx2txt`：文本与页码解析。
- Redis 任务：解析状态。
- Chroma + Embedding：仅对超长文档或跨文档课程启用。

### 14.3 文件安全

- 只允许 `.pdf` 和 `.docx`，不信任客户端 MIME，校验扩展名、magic bytes 和解析结果。
- 建议限制 10 MB、50 页；超限要求用户拆章节。
- COS 使用私有读写，不返回永久公网 URL。
- 上传文件名必须规范化，存储 key 由服务端生成。
- 文档中的命令只是资料，Prompt 边界与 injection 测试不得删除。

### 14.4 页码证据模型

```python
class DocumentBlock(BaseModel):
    block_id: str
    page_number: int | None
    paragraph_index: int
    text: str
    start_offset: int
    end_offset: int

class Evidence(BaseModel):
    quote: str
    document_id: str
    block_id: str
    page_number: int | None
    start_offset: int
    end_offset: int
```

不完全信任 LLM 返回的页码和 offset，服务端必须根据 block 重新定位。

### 14.5 接口

```text
POST   /api/v1/training/documents

POST   /api/v1/training/documents/{document_id}/generate
GET    /api/v1/training/drafts/{quiz_id}

POST   /api/v1/training/drafts/{quiz_id}/approve
```

审核页必须支持：

- 查看原文和页码。
- 修改题干、选项、答案和解析。
- 删除单题。
- 标记准确/有歧义/不符合原文。
- 对高风险题显式勾选“已核对门店制度”。
- 只有全部必须审核项通过才允许发布。

### 14.6 检索决策

```text
解析文本 <= 模型安全上下文阈值
  → 直接整文/分章节出题

单文档超长
  → 按标题与页码分章节

```

不要默认对所有 10 页手册使用向量数据库，这会增加检索遗漏、成本和部署复杂度。

- PDF/DOCX 上传、解析、出题、审核和确认流程在真机通过。
- 原文引用页码正确。
- 文件不因容器重启丢失。
- 不支持格式、加密 PDF、扫描 PDF 给出明确提示。OCR 不放入首版，除非试用数据证明必须。

## 16. M5：生产硬化与小程序发布

### 16.1 安全

- 限制文本、文件、请求体、题数和 Agent 迭代次数。
- 上传扫描、magic bytes、文件名规范化和私有 COS。
- JWT secret 至少 32 字节，生产不使用默认值。
- 登录、出题、上传、提交答案和邀请码均限流。
- 系统错误不暴露密钥、供应商原始错误或 SQL。
- 日志只保存输入长度/哈希，不保存完整手册和用户答案中的个人信息。
- 每条数据访问验证 `store_id`，增加横向越权测试。

### 16.2 可观测性

每次 Agent 任务记录：

- `request_id/task_id/thread_id`。
- 输入长度和内容哈希。
- model/prompt/graph 版本。
- 各节点耗时、token 和重试次数。
- 程序校验与 Critic issue 类型。
- 修订次数与最终人工结论。
- 供应商错误分类，不记录原始响应中的敏感信息。

告警：

- 连续任务失败。
- P95 超时。
- 当日模型预算达 80%/100%。
- Redis/MySQL/COS 不可用。
- 人工审核积压。

### 16.3 微信上线

- 正式 AppID、request/upload/download 合法域名。
- 服务类目、名称重名/商标、ICP 与届时 AI 生成内容规则核验。
- 用户协议、隐私保护指引、文件用途和保留期说明。
- 内容安全检查和投诉/删除入口。
- 体验版先做弱网、切后台、登录过期、重复提交和大文件验收。

### 16.4 性能与容灾

- 生成接口立即返回 task ID，禁止在 HTTP 请求中长时阻塞。
- 工作进程与 API 进程可独立扩缩容。
- 模型供应商故障时保留草稿和已生成结果，不伪装为 AI 已成功。
- 生成报告的 AI 失败不阻断基础成绩返回。
- MySQL 备份和恢复演练；COS 文件生命周期；Redis 只存可重建状态。
